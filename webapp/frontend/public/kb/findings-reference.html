Findings reference

What the engine checks

Every finding in your report comes from one of these deterministic rules. Each cites the exact metric that triggered it; severity scales with the size of the problem. Thresholds are tunable and calibrated to avoid false positives.

Queries Query rules

RuleFindingTriggers when
R-Q1One query consumes a large share of total database timeA single query digest accounts for ≥20% of total database time (escalates to critical at ≥40%). The highest-leverage query to fix first.
R-Q2Query is slow on every executionMean latency is high (≈1s+) on every call; severity scales with call volume.
R-Q3Query runs at very high frequencyA query is called extremely often (tens of thousands of times a day+), so even a small per-call cost compounds.

Indexes Index rules

RuleFindingTriggers when
R-I1Table is scanned in full by frequent queries (missing index candidate)A large table (≥100 MB) takes many sequential scans, or reads far more rows than it returns. The headline finding of most audits.
R-I2Index is never used but costs space and write timeAn index of meaningful size (≥20 MB) has effectively zero reads — pure overhead on every write.
R-I3Redundant index duplicates another index's leading columnsOne index's columns are a leading-prefix subset of another, so it can usually be dropped.

Ops Operational-risk rules

RuleFindingTriggers when
R-L1Sessions were blocked waiting on locksLock waits exceeded a multi-second threshold — a sign of contention that stalls users.
R-C1Connection usage is close to the configured limitPeak connections reached ≥80% of the limit (critical at ≥90%) — headroom risk before connection errors.
R-G1Table is growing fastA large table grew by ≥25% over the comparison window — capacity and future-performance signal (needs a delta snapshot).

Maintenance Maintenance rules

RuleFindingTriggers when
R-M1Dead tuples accumulating faster than vacuum reclaims (PostgreSQL)Dead-tuple ratio on a sizeable table is high — vacuum is falling behind.
R-M2Autovacuum disabled or never processed an active table (PostgreSQL)An active table has never been vacuumed, or autovacuum is off.
R-M3Table likely carries reclaimable bloat, estimated (PostgreSQL)Estimated bloat on a large table crosses the reclaim threshold.
R-M4Table carries significant reclaimable space / fragmentation (MySQL)data_free is a large fraction of a big table's size — an OPTIMIZE TABLE candidate.

Config Configuration rules

The configuration check (R-CFG-PG / R-CFG-MY) evaluates a whitelist of performance-relevant settings against your database's actual size and workload — it never flags a setting in the abstract.

EngineSettings evaluated (examples)
PostgreSQLshared_buffers, work_mem × max_connections, effective_cache_size, autovacuum scale factors, max_connections, checkpoint_completion_target
MySQL / MariaDBinnodb_buffer_pool_size vs. data size and buffer-pool hit ratio, redo log file size, table-open-cache churn, thread-cache efficiency, max_connections
Why thresholds are conservative False positives erode trust faster than anything else, so every threshold is tuned to fire only on real, sizeable problems — and each finding names the number that triggered it so you can judge it yourself.
