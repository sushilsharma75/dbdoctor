Security & privacy

What leaves your environment — and what never does

The whole product is built around one promise: your credentials and your data stay on your side. Here is precisely how that holds.

We never receive your credentials

There is no connection string field anywhere in DBDoctor, and no agent that phones home. The collector runs inside your environment, under an account you control. DBDoctor never opens a session against your database — you do.

The only thing you send us A single snapshot.json file that you generate locally and can inspect byte-for-byte before uploading.

The collector is read-only, by construction

  • It opens a read-only session and reads statistics/catalog views only — never your table rows.
  • It contains no write statements of any kind. You can grep the single file to confirm this yourself before running it.
  • It prints its own SHA256 at startup, so you can verify the file you ran is the file we published and hasn't been altered.
  • It needs only statistics grants — see the PostgreSQL and MySQL guides for the exact, minimal privileges.

Literals are stripped at the source

Query text is never captured raw. Both the database's own statistics views (pg_stat_statements, performance_schema digests) and the collector itself normalize statements so that every literal value is replaced by a placeholder before anything is written to the snapshot. 

-- what your app ran
SELECT * FROM orders WHERE customer_id = 84213 AND status = 'shipped';

-- what the snapshot contains
SELECT * FROM orders WHERE customer_id = ? AND status = ?;

Because stripping happens on your machine, parameter values never leave it — even transiently.

You can verify everything before uploading

  1. Read the collector — it is one file, plainly written, with no repo dependencies beyond a single database driver.
  2. Check the printed SHA256 against the published value.
  3. Open snapshot.json in any editor. Everything we receive is in that file; nothing is hidden or sent separately.
Settings whitelist The collector reads only an explicit allowlist of performance-relevant settings (for example shared_buffers, work_mem, innodb_buffer_pool_size). It does not sweep your full configuration, so credentials, replication secrets, and unrelated parameters are never captured.
